# Enable Banking AIS Integration Plan

**Status:** Proposed post-MVP capability; requires product, provider, legal/privacy, and operational approval before implementation or production activation.

## 1. Goal, scope, and non-goals

Enable household members to connect supported bank accounts through Enable Banking's Account Information Service (AIS), retrieve external transactions into a shared review inbox, and record only user-confirmed facts through Family Budget's existing server-side accounting path. The integration supports both the Angular web client and native Android client, with the Go API remaining the trust, authorization, import, and posting boundary.

This is a **reviewed scope extension**, not current MVP scope. `MVP_SCOPE.md` explicitly defers direct bank APIs and account aggregation, and the accounting/domain specifications describe suggestion ingestion as future capability. Adoption requires an explicit scope review and approval; this plan does not silently redefine the MVP.

Initial capability boundary:

- **AIS/read-only only.** Obtain consented account information and transactions; do not initiate payments or alter bank accounts.
- **No Payment Initiation Service (PIS).** Exclude payment creation, submission, and payment API credentials/permissions from product and implementation scope.
- **No automatic posting.** Imported bank activity is an unposted, unreserved candidate. A person must review and confirm it before any financial operation is committed.
- **No automatic categorization or guessed ledger effects.** Unknown or ambiguous direction, account, amount, date, currency, or transaction type remains unresolved in the inbox.
- No bank credentials, Enable Banking JWTs, RSA signing key, or other provider secrets in Angular, Android, browser storage, or mobile app packages.
- No mandatory historical import during household onboarding; no imported bank balance may silently become an opening balance or overwrite a derived Family Budget balance.

## 2. Current backend fit and gaps

The existing transaction-suggestion domain and API contract provide a useful workflow foundation: household-scoped list/create/edit/dismiss operations, no postings or reservations while unconfirmed, and an idempotent confirmation operation that records a completed external purchase through the shared financial path. The contract also separates committed journal operations from suggestions and requires household authorization and idempotency for financial confirmation (`DOMAIN_MODEL.md` §§3.7–3.10; `STATE_TRANSITIONS.md` §4; `openapi.yaml` suggestion endpoints).

However, the current suggestion contract is intentionally small: its candidate shape has source, amount, merchant, state, and cancellation metadata. It does not carry the external account mapping, effective date, credit/debit direction, transaction status, bank reference/fingerprint, or durable import provenance needed for bank synchronization and safe deduplication. The current confirmation request is purchase-oriented and requires a purchase kind/account/envelope; it does not provide a matching income-confirmation path. Manual suggestions are user-entered candidates, **not bank-import records**; importing by pretending a bank record is a manual suggestion would lose source identity and make synchronization, deduplication, disconnect, and audit behavior unreliable.

Before launch, either enrich the suggestion domain/API for imported candidates while preserving its existing lifecycle, or introduce dedicated import records linked to suggestions (recommended below). Add explicit confirmation routing for income and other supported factual transaction kinds, while keeping every confirmed event on the existing validated posting path. Update OpenAPI, persistence migrations, authorization, idempotency, audit, and tests together. These are design gaps, not claims about already implemented functionality.

## 3. Target architecture and persistence boundary

```text
Angular / Android
       │ authenticated Family Budget API; browser/system-browser redirect only
       ▼
Go API ───────► Enable Banking API (AIS)
   │                    ▲
   │ durable jobs       │ signed server-side requests
   ▼                    │
PostgreSQL ◄──── sync worker(s) ──┘
   │
   └── imported candidates → suggestion inbox → user confirmation → shared posting path
```

- Angular and Android call only the Family Budget API. The Go API initiates consent, owns the callback, exchanges the returned code, persists session/account associations, and schedules bank reads. The Enable Banking private key is used only by trusted backend processes.
- Use a durable worker/polling design for background transaction retrieval, not client polling of Enable Banking. Persist sync jobs or an equivalent outbox in PostgreSQL; lease work with expiry, serialize per linked bank account/session, and make retries safe. API instances can enqueue work; a worker can run separately or as a separately controlled backend process.
- Provide a public HTTPS callback route on the Go service/reverse proxy. It validates and consumes the pending authorization state before exchanging a code server-to-server. Do not accept a callback result from a client as proof of authorization.
- Generate short-lived RS256 JWTs as needed. Enable Banking's API reference specifies a registered application id as JWT `kid`, `iss=enablebanking.com`, `aud=api.enablebanking.com`, and a maximum 24-hour TTL. Use a substantially shorter operational TTL where practical.
- Provision the RSA private key outside source control and images, e.g. a root/service-account-readable secret file mounted read-only or an approved secrets service. Restrict access to the API/worker components that sign provider requests; define rotation, backup/custody, and incident revocation. Never place the key in PostgreSQL, a CI artifact, a client config, or logs.

### Proposed logical records

Names and columns are conceptual pending domain/schema review; PostgreSQL migrations remain the schema authority.

| Record | Required responsibility and candidate data |
|---|---|
| `bank_connections` | Household and provider boundary; selected ASPSP name/country (the API identifies an ASPSP by name + country, not a durable unique bank id); connection state; initiating actor and timestamps; current provider session and its expiry; consent/auth attempt status; safe failure/retry summary. Store provider session identifiers and other sensitive values encrypted at rest or otherwise protected, with strict access controls. |
| `linked_bank_accounts` | Connection/session relationship; provider account id (session-scoped); provider identification hashes for rematching; limited account display metadata; currency/type; selected Family Budget account mapping; active/archive status. Do not use display name or masked account number alone as identity. Reject or explicitly handle currency/account types unsupported by the single-currency domain. |
| `bank_sync_state` | Per linked account last successful window, next eligible fetch time, last error class, backoff/rate-limit state, coverage/history boundary where known, and durable job/continuation progress. Continuation keys are transient provider cursors: protect them as sensitive state, bind them to the exact request parameters, and delete them when exhausted or abandoned. |
| `external_transaction_imports` | Durable normalized source record keyed by household + linked bank account + conservative source fingerprint; provider status (e.g. pending/booked), source references when present, direction, exact minor-unit amount/currency, effective-date candidate, merchant/remittance candidate, first/last-seen times, review/dismiss state, and optional linked suggestion and committed journal operation. Preserve enough dismissed/import history to suppress resurface on every sync, subject to an approved retention policy. |

The import record is not a journal operation and never affects balances. Avoid persisting the complete Enable Banking response: retain only fields needed for review, traceability, matching, and operational support. If temporary raw response retention is proven necessary for debugging, make it disabled by default, access-controlled, encrypted, redacted, short-lived, and explicitly approved.

## 4. User experience

1. **Connect:** A household member chooses “Connect a bank,” selects a country and supported bank from current ASPSP data, sees a clear disclosure of data requested, controller/privacy information, sync behavior, and disconnect/revocation controls. Do not promise coverage until verified for the target bank/account type.
2. **Bank SCA and consent:** The backend starts an AIS authorization. The web client navigates the browser and Android opens the system browser/custom tab (not an embedded WebView) to support bank/app SCA hand-offs. The callback returns to the backend and then the app receives a safe completion result/deep link with no provider code or key.
3. **Select and map accounts:** Show accounts returned for the new session, ask which to link, and map them explicitly to existing household accounts or create a local account only through a clearly reviewed account-setup flow. Display bank account identity carefully. Do not merge accounts based on name/amount guesses; enforce the household's single-currency and account eligibility rules.
4. **Sync:** Explain initial history coverage and ongoing refresh status. Show when last sync ran, when another background refresh is allowed, and when user-present refresh may be available. Make sync status distinct from transaction confirmation.
5. **Review inbox:** Present imported activity as unposted suggestions with source account, bank, status (pending/booked), bank-provided date, signed direction, amount/currency, merchant/remittance text, and ambiguity warnings. Do not auto-assign an envelope or infer income/refund/transfer when data is uncertain.
6. **Confirm/edit/dismiss:** A user corrects details and chooses the appropriate factual transaction flow, then confirms through the normal API with idempotency. Purchases, income, refunds, transfers, and other event kinds must use their existing or newly specified domain command; insufficient budget funding does not erase actual external activity. Ambiguous items remain suggestions until corrected. Dismissal records a source disposition/fingerprint so routine sync does not recreate it.
7. **Disconnect/reauthorize:** Provide an explicit disconnect action and consent-expiry warnings. Disconnect stops future reads, cancels queued work, and attempts session deletion where supported; it does not erase already committed journal history. Expired/early-expired sessions enter reauthorization, which may return new session-scoped account ids and must rematch safely.

## 5. Authorization and callback flow

1. An authenticated client requests a connect attempt for a household. The backend authorizes active membership, records actor/household/selected ASPSP and a bounded pending attempt, and creates a cryptographically random, unguessable `state` (at least 128 bits of entropy; 256 bits preferred). Bind it server-side to the attempt, expected callback, initiating principal/session context and short expiry. Store only a hash where feasible.
2. The backend calls `GET /aspsps` for current bank availability and `POST /auth` with the selected ASPSP, AIS-only access, exact registered callback URL and state. It persists the returned authorization id/redirect URL and returns only what the client needs to begin navigation. Do not send Enable Banking API authorization JWTs or signing material to a client.
3. Register and enforce an **exact HTTPS callback URL allowlist**: fixed scheme, host, port and path; no wildcard hosts, open redirects, user-controlled callback URL, or arbitrary return URL. Enable Banking also requires registered redirect URLs. Route any post-callback return to a fixed allowlisted web URL or application link.
4. At callback, validate parameter shape and atomically consume the state exactly once before processing. Check attempt expiry, matching household/user attempt and expected status. Reject replay, missing/duplicate/mismatched state, and invalid callback combinations. Treat `error`/`error_description` as untrusted data; do not expose provider text directly to users.
5. Exchange the one-time `code` with backend-signed `POST /sessions`. Validate that the returned session and accounts belong to this attempt, persist provider session, expiry, account ids and identification hashes, and enqueue initial sync only after successful persistence. The `code` must never be sent to Angular/Android, stored in URLs beyond the callback handling window, or logged. Redact callback query strings at the proxy and application layers.
6. Scope each Enable Banking account id to the session that returned it. Do not assume an account id persists on reauthorization: the provider documents that both session and account ids change. On reauthorization, compare provider `identification_hash`/`identification_hashes` against previously held hashes to propose a rematch; require safe unambiguous matching, otherwise present accounts for explicit mapping. Hash matching is a provider-supported identity signal, not permission to merge unrelated household records.

## 6. Import normalization and synchronization rules

- Normalize provider amounts from decimal strings using exact decimal parsing into integer minor units; reject unsupported/mismatched currency rather than using floating point or silently converting FX. Preserve provider credit/debit indicator separately and map signs according to account kind and an explicit transaction-type review. Bank data can describe card repayments, transfers, refunds, income, fees, and other events; merchant text alone does not decide accounting treatment.
- Preserve provider transaction status. `BOOK` and `PDNG` are distinct facts. Recommended initial policy: only booked transactions are confirmable as final financial facts; pending entries may be shown as provisional and updated/hidden as the bank changes them, but must not be posted. Pending-to-booked matching is permitted only with a reliable stable reference for that ASPSP/account; otherwise leave it visible for review and avoid auto-merging. Final pending policy remains an approval question.
- Select the effective date from documented bank date fields using a deterministic, provider-tested policy (e.g. booking date for booked transactions); preserve source dates and the Family Budget effective date separately. `EffectiveDate` remains a household-local `YYYY-MM-DD` fact and is never inferred by converting an audit instant. Ask for correction rather than choosing among conflicting/missing dates.
- Follow every non-null `continuation_key` until it is absent, including responses with zero transactions. Keep all other query parameters unchanged across pages. Persist page processing and deduplication atomically enough that a retry cannot lose a page or duplicate imports; detect repeated cursor loops and alert rather than spinning indefinitely.
- Use overlapping date windows on recurring sync to catch late-posted and corrected activity; keep a durable lower watermark with a conservative overlap, and periodically reconcile provider changes within the permitted history window. Advance a watermark only after all continuation pages have been processed. The exact overlap and fallback behavior should be tested per target ASPSP.
- Do not treat `transaction_id` as a stable deduplication key: the provider documents it for transaction-detail lookup and it may change between list reads. `entry_reference` is useful where present but not universal and may be absent or duplicate; it is not globally unique. Prefer a scoped key using the linked-account identity and `entry_reference` where trustworthy, with status/evolution handling. Where no reliable id exists, use a conservative fingerprint of normalized account identity, amount/currency, direction, date/status and selected normalized descriptors; collisions/near matches must be surfaced for review rather than silently discarded. Identical merchant/amount pairs can be distinct purchases.
- Maintain separate import states for observed, candidate/suggestion-created, dismissed, matched/confirmed, and duplicate/superseded as appropriate. An import retry must not create a second suggestion or journal event. A confirmed import is linked to the immutable operation; a later change is handled as a correction/reversal/new factual event, never by rewriting a committed journal entry.
- Use `strategy=longest` only for a deliberate initial/history fetch and `strategy=default` for ongoing recent windows. Available history varies by bank, account, authorization timing and strategy; no initial history range is guaranteed. Test/record the observed coverage and present gaps honestly. Do not silently retry a failed historical query with a shorter date range and imply complete history.
- Treat provider/ASPSP 429 and other transient errors as distinct rate-limit/outage conditions. Queue per account, apply bounded exponential backoff with jitter and `Retry-After` where supplied, honor bank restrictions and avoid synchronized retry storms. Enable Banking reports that many ASPSPs limit background reads to around four per day; user-present fetches are distinguished by PSU headers. When a user initiates a live fetch, supply the full required/available PSU headers consistently for that actual user-present request; scheduled worker requests should not impersonate a present PSU and should send none. Confirm bank-specific requirements from current ASPSP metadata.

## 7. Domain and API changes required

1. Choose between extending `TransactionSuggestion` and adding `external_transaction_imports` linked to `TransactionSuggestion`. The recommended separate import record keeps source lifecycle and synchronization/deduplication independent of suggestion editing and preserves dismissed/confirmed source identities. Suggestions remain the shared review surface; no import record itself is postable.
2. Add household-scoped APIs for ASPSP discovery (or a safe server-cached projection), connect-attempt creation, linkable-account listing/mapping, sync status/manual refresh, connection listing, disconnect, and reauthorization. Callback is a provider-facing backend route, not an authenticated client callback API. The exact OpenAPI contract, error codes, pagination and owner/member permissions require review.
3. Extend suggestion candidate fields with source/import id, linked local account, transaction direction/kind candidate, amount/currency, candidate effective date, pending/booked status, merchant/remittance candidate and confidence/ambiguity. Preserve user edits and source values distinctly. Keep the current guarantee that suggestions have no postings and no reservations.
4. Add explicit income confirmation (and reviewed routing for transfers, refunds and card events if in scope). Current suggestion confirmation is purchase-only; do not misclassify every credit as income. Unknown/ambiguous data remains an unconfirmed candidate. Each confirmation uses the shared posting implementation, household-scoped idempotency key and transaction/concurrency controls.
5. Preserve provenance from import through confirmation to `JournalOperation`/posting: source kind/provider, linked import id, source account, relevant external reference or fingerprint, actor who confirmed, recorded timestamp, effective date, correction links, and idempotency outcome. Journal/postings remain append-only. Corrections are compensating/replacement operations or metadata audit records as specified, never in-place edits.
6. Every import, link, connection, account mapping, reauthorization and disconnect is server-authorized against the household. Never trust a client household id, remote account id, or suggested local account id without same-household validation. Make membership removal revoke ongoing access according to an approved policy.
7. Use durable idempotency and database uniqueness/locking for concurrent connect callbacks, sync retries, duplicate imports, confirmation and disconnect. A confirmed transaction cannot be posted twice, even if the worker/client retries or the user confirms concurrently from web and Android.
8. Record no unnecessary raw provider response, access credentials, full account identifiers, PSU headers, authorization code, or consent content in audit logs. Store only minimized, justified source data; document field-level retention/deletion and encrypted secret/session storage before migrations are approved.

## 8. Security, privacy, legal, and operations gates

- **Authorization and actor attribution:** enforce household scope on every API and background job. Capture the initiating/confirming actor; workers do not become the actor for ledger confirmation. Define who can connect, map, view, refresh, reauthorize and disconnect; do not assume any member capability without review.
- **Secrets and data at rest:** protect the private key separately from application data; encrypt provider session ids and any sensitive identifiers at rest; restrict database and backup access; rotate credentials; maintain encrypted off-host backups and test restore without broadening operator access. Scrub secrets, codes, full account identifiers, personal transaction text and callback query values from logs, traces, metrics and error reports.
- **Web/mobile security:** TLS only; fixed callback and return URL allowlists; CSRF/state/replay protection; no open redirects; safe browser-based SCA handoff; short-lived client state; strict content/referrer handling on callback pages. Never embed Enable Banking private keys or signed API JWTs in either client.
- **Consent and revocation:** store minimum consent/session metadata and expiry. Warn before known expiry, handle early `EXPIRED_SESSION`, and require PSU reauthorization rather than retrying forever. Support user revocation via Family Budget disconnect and best-effort provider session deletion; Enable Banking notes a bank may not always permit immediate session deletion. Reconcile provider portal revocation on the next fetch/error and stop reads promptly.
- **Retention and deletion:** agree retention periods for raw/minimized imported data, dismissed items, fingerprints, connection metadata, security/audit records, and backup copies. On disconnect, cancel jobs and delete/revoke session secrets and unneeded link data; keep committed journal provenance and accounting history under a separately reviewed legal retention policy. Define household deletion and subject-request procedures before launch.
- **Legal/controller review:** Enable Banking's public Knowledge Base says that under its AISP setup Enable Banking is also a data controller and the receiving application remains a controller for data it receives; obtain counsel/privacy review of roles, data sharing, lawful basis, consent, DPIA if appropriate, cross-border processing, user notices, terms and privacy policy. Do not assume Enable Banking's status removes Family Budget's obligations. Production application information includes service description, privacy/terms URLs, and a data-protection contact in the provider registration requirements.
- **Provider activation and commercial gate:** public production use may require provider contract and KYB/business approval. Restricted production linked-own-account mode is for whitelisted linked accounts only; it must not be assumed to support a public/shared-household launch. Provider describes pricing as volume-based on connected accounts/month (and payments for PIS) with minimum invoicing; confirm current written quote, minimum, eligible countries/accounts, contract terms, and cancellation/retention obligations before the production go/no-go. AIS-only scope does not include payments.
- **Reliability:** monitor sync lag, success/error rates by ASPSP (without personal data), rate limiting, expired sessions, queue age, callback failures, duplicate/fingerprint ambiguity, and secret rotation. Add alerting and an operator runbook for provider/bank outages, 429 throttling, stuck cursors, consent revocation, leaked credentials and incident notification. Bound every retry/page loop and make workers safe under restart and concurrent deployment.

## 10. Open questions requiring approval

1. Which target countries, ASPSPs, account types and personal/business user types are in the first supported set, and what observed coverage qualifies a bank for launch?
2. Will Enable Banking offer and contract for this public shared-household use case; what KYB/legal entity, production contract, restricted-mode limitations, connected-account definition, minimum invoice and current written price apply?
3. What background frequency should Family Budget request, given many ASPSPs allow only about four background fetches per day? Which user-present refresh behavior is acceptable, and what is the per-bank operational policy?
4. Who may create/manage a connection: owner only, any active household member, or connector plus owner? Who may select accounts, reauthorize, disconnect, and see bank/account metadata? What happens when the connecting member leaves the household?
5. How should a confirmed incoming credit be classified: income, transfer, refund, reimbursement or another type; which data or user choices are required before commit? Which other transaction classes are supported in initial release?
6. Are pending transactions displayed at all? If displayed, are they non-confirmable until booked, and what matching evidence permits pending-to-booked replacement without duplicate inbox entries?
7. What initial history range is offered, if any, and how should unavailable/partial bank history be communicated? Is `longest` history fetch expected at authorization or only on explicit request?
8. What retention periods apply to imported candidates, dismissed fingerprints, provider identifiers/session secrets, audit records and backups? What user disconnect, account unlink, household deletion and data-subject deletion behaviors are required?
9. Which widget/redirect flow is approved for web and Android, and what exact allowed origins and callback/deep-link hosts will be registered? Prefer backend-created redirect plus system browser unless usability/security testing supports widgets; widget origins must be allowlisted.
10. Is importing balances in scope at all? If later added, how will bank-reported balances remain read-only and separate from server-derived ledger balances and reconciliation operations?
